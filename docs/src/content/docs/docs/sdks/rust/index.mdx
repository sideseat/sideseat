title: Rust SDK
description: Send traces, sessions, and conversations from Rust AI applications to SideSeat in one call.

`sideseat` is an OpenTelemetry distribution for Rust. One call configures tracing, metrics, and logs for
a SideSeat project, and a session scope attributes every span - including spans libraries create - to the
right session and user.

## Install

```bash
cargo add sideseat
cargo add tokio --features full
```

Rust 1.94.1 or newer. Start a local server with `npx sideseat`.

## Quick start

```rust
use std::time::Duration;

use sideseat::{Options, Session, SpanOptions};

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let telemetry = sideseat::init(Options::new().service_name("travel-agent"))?;

    let conversation = Session::new("conversation-42").user("user-7");
    conversation
        .scope(telemetry.trace("plan-trip", SpanOptions::new(), || async {
            run_agent("Plan a weekend in Lisbon.").await
        }))
        .await?;

    telemetry.shutdown(Duration::from_secs(5));
    Ok(())
}
```

`init` points OpenTelemetry at `http://127.0.0.1:5388` and the `default` project, and installs the
global tracer and meter providers. Call it before any library creates its first span.

## Sessions and users

A `Session` is a scope, not a span. Every span started inside it - by your code or by any library that
uses the global tracer - gets `session.id` and `user.id`:

```rust
let conversation = Session::new("conversation-42").user("user-7");

conversation.scope(agent.turn("What should I eat there?")).await;   // async code
let _entered = conversation.enter();                                // synchronous code on this thread
```

The values travel in the OpenTelemetry context, so they follow a future across `.await` points. A task
started with `tokio::spawn` does not inherit the context; scope the spawned future too. They are never
sent as W3C baggage, which HTTP instrumentation would forward to model providers. A nested session
overrides the outer one for its duration.

## Traces and spans

```rust
use sideseat::{KeyValue, SpanKind, SpanOptions};

telemetry
    .trace("plan-trip", SpanOptions::new().session(Session::new("s-1")), || async {
        let documents = telemetry
            .span(
                "retrieve-context",
                SpanOptions::new()
                    .kind(SpanKind::Client)
                    .attribute(KeyValue::new("app.documents", 4_i64)),
                || load_documents(),
            )
            .await?;
        answer(documents).await
    })
    .await?;
```

`trace()` always starts a root span, keeping the current session unless its options name another.
`span()` starts a child of the active span. Both return the closure's result; an `Err` marks the span as
failed and records the error message.

## Recording model calls

Rust has no framework integrations. Record a model call as a span that follows the
[OpenTelemetry GenAI conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/), and SideSeat
reads the conversation from it:

```rust
telemetry
    .span(
        "chat claude-sonnet-5-5",
        SpanOptions::new().kind(SpanKind::Client).attributes([
            KeyValue::new("gen_ai.operation.name", "chat"),
            KeyValue::new("gen_ai.provider.name", "aws.bedrock"),
            KeyValue::new("gen_ai.request.model", "global.anthropic.claude-sonnet-5-5"),
            KeyValue::new("gen_ai.input.messages", input_json),
            KeyValue::new("gen_ai.output.messages", output_json),
        ]),
        || async { Ok::<_, std::io::Error>(()) },
    )
    .await?;
```

`telemetry.captures_content()` reports the content-capture setting; check it before recording prompts
and responses.

## Configuration

Explicit options win over environment variables, which win over defaults.

| Option | Environment | Default |
| --- | --- | --- |
| `endpoint` | `SIDESEAT_ENDPOINT`, then `OTEL_EXPORTER_OTLP_ENDPOINT` | `http://127.0.0.1:5388` |
| `project` | `SIDESEAT_PROJECT_ID` | `default` |
| `api_key` | `SIDESEAT_API_KEY` | none |
| `service_name` | `OTEL_SERVICE_NAME` | `sideseat-app` |
| `service_version` | `OTEL_SERVICE_VERSION` | the SDK version |
| `capture_content` | `SIDESEAT_CAPTURE_CONTENT` | on |
| `disabled` | `SIDESEAT_DISABLED` | off |
| `debug` | `SIDESEAT_DEBUG` | off |
| `resource_attribute` | `OTEL_RESOURCE_ATTRIBUTES` | none |

Booleans accept `1/0`, `true/false`, and `yes/no` in any case; anything else is an error at `init`.

An endpoint without a path is a SideSeat server: signals go to `{endpoint}/otel/{project}/v1/{signal}`.
An endpoint with a path is already an OTLP base: signals go to `{endpoint}/v1/{signal}`. Headers from
`OTEL_EXPORTER_OTLP_HEADERS` are kept, and the API key is sent as `Authorization: Bearer <key>`.

## Logs

OpenTelemetry Rust has no global logger provider, so log records reach SideSeat through an appender built
on `telemetry.logger_provider()`, for example `opentelemetry-appender-tracing`.

## Lifecycle

- Calling `init` again with the same settings returns the same client; different settings return
  `Error::AlreadyInitialized`. After `shutdown`, `init` configures a new pipeline.
- `flush()` and `shutdown(timeout)` return whether everything was exported. `shutdown` is idempotent,
  and the pipeline also shuts down when the last clone of the client drops.
- When disabled, closures still run, spans are non-recording, and nothing is exported.

## Testing your application

Turn export off and add an in-memory exporter from `opentelemetry_sdk` (feature `testing`):

```rust
use opentelemetry_sdk::trace::{InMemorySpanExporter, SimpleSpanProcessor};

let spans = InMemorySpanExporter::default();
let _telemetry = sideseat::init(
    Options::new()
        .export(false)
        .span_processor(SimpleSpanProcessor::new(spans.clone())),
)?;
```
