SideSeat treats telemetry compatibility as an executable contract, not a list of logos. Raw
OTLP requests captured from SDKs and frameworks are replayed through the production ingestion,
storage, query, SideML normalization, deduplication, and ordering paths.

## Production message rubric

Every captured sample receives a binary result for every applicable criterion. A sample is
accepted only when all of them pass; unrelated successes cannot average away a missing or
misordered message.

| Criterion | Required evidence |
| --- | --- |
| Wire fidelity | The fixture is the exact OTLP request emitted by the tested SDK or framework |
| Framework identity | Each native framework suite reaches its declared framework label without SDK fallback |
| Span view | Each span returns only its own messages, in source order |
| Trace view | The complete conversation is ordered and scoped to one trace |
| Session view | Traces partition one session exactly; a trace cannot belong to two sessions |
| Project feed | The same messages appear once in the documented feed order |
| Content | Full canonical content digests match, not only previews or counts |
| Tool causality | Every identified result follows one matching call and is answered once |
| No duplicates | Re-sent history, redundant carriers, and repeated delivery add no copy |
| Determinism | Re-run, reversed arrival order, and cache hits produce the same result |
| SDK parity | Language SDK/OTel and framework SDK/native pairs match requests, span projections, trace topology, sessions, and feed |

The ordering tests also inject contradictions, repeated identical calls, redundant state
snapshots, and reversed delivery. Property tests require the resolver to return a permutation
of the surviving messages rather than silently inventing or dropping content.

## What SDK parity proves

Each language pair emits the same canonical conversation:

1. a user asks a question;
2. an assistant announces a tool call;
3. the tool call and result are correlated by ID;
4. the assistant gives the final answer;
5. every span carries the same session and user correlation.

The gate compares normalized span, trace, session, and project-feed output. This catches
exporter endpoint mistakes, missing resource attributes, broken parenting, correlation loss,
duplicate instrumentation, and message-order differences that a basic “request arrived”
smoke test cannot detect.

In the current Logfire 6 wire shape, the input-only streaming lifetime span and completed
streaming log are emitted separately. Logfire's default context makes the response an unrelated
root trace. Both the native control pipeline and SideSeat reparent it before OTLP export, because
the server cannot safely infer that relationship later. Framework pairs must agree on request and
span counts, complete trace topology, every span projection, session content, and the project feed.

## Raw preservation and read-time parsing

The server stores the original span events and attributes. Producer-specific message parsing,
SideML conversion, deduplication, and ordering happen when data is read. Parser fixes therefore
apply to historical telemetry without rewriting or recapturing stored spans.

Extracted indexing fields such as model, framework, token usage, and session membership are
derived during ingestion, while raw producer data remains available through raw-span query
options.

## Local reproduction

Credential-free SDK parity captures can be regenerated with:

```bash
make capture-sdk-conformance-python
make capture-sdk-conformance-javascript
make capture-sdk-conformance-dotnet
make capture-sdk-conformance-rust
```

Run the complete message gate with:

```bash
cargo test --locked -p sideseat-server --test message_goldens
```

Framework captures that call real models require the corresponding provider credentials. CI
uses committed OTLP payloads, so verification remains deterministic and does not make paid or
network-dependent model calls.
